1. Executive Summary & Architecture

This project delivers a complete, production-grade backend service for diagnostic centre test catalog management, patient bookings, simulated payment execution, and strictly idempotent payment webhook processing. Built with a clean, layered architecture separating HTTP controllers, domain services, persistence models, and DTO schemas.

Layered Architecture

  • app/api/v1/: RESTful route controllers & validation.
  • app/services/: Isolated business domain logic.
  • app/models/: SQLAlchemy 2.0 Async declarative ORM models.
  • app/schemas/: Pydantic v2 schemas for request/response typing.

Key Highlights

  • JWT Authentication with bcrypt password hashing.
  • Flexible Pricing Junction (Centre × Test).
  • Immutable Price Snapshot on bookings.
  • Idempotent Webhook Engine with race condition safety.
  • 26 Integration Tests with 100% pass rate.

3. Booking State Machine & Invariants

The booking lifecycle enforces strict state transition guards:

  • PENDING → Initial state upon booking creation. Awaiting simulated payment or gateway webhook.
  • CONFIRMED → Transitioned atomically when payment succeeds. Cannot be double-paid.
  • FAILED → Transitioned when payment fails. User may retry payment.
  • CANCELLED → Patient cancellation. Late-arriving webhooks cannot revive a cancelled booking.

4. Simulated Payment Service & Webhook Idempotency

A. Direct Simulated Payment (POST /payments/)

Allows patients to simulate payments directly:

  • Validates booking exists and verifies authorization (patients can only pay for their own bookings).
  • Guards against invalid states: Rejects payments on already CONFIRMED or CANCELLED bookings (400 Bad Request).
  • Atomically writes a Payment record with a unique transaction reference and updates booking status.

B. Payment Webhook Engine (POST /payments/webhook/)

Payment providers (Stripe, Razorpay) deliver webhooks with at-least-once delivery. Our implementation guarantees strict idempotency:

  1. Deduplication Check: Queries webhook_events by event_id. If already processed, immediately returns 200 OK with {"status": "DUPLICATE_IGNORED"} without creating duplicate payments or re-triggering transitions.
  2. Database-Level Uniqueness: event_id is guarded by a database unique index.
  3. Concurrency & Race-Condition Safety: If two duplicate webhooks arrive concurrently, the second catches an IntegrityError, performs a transactional rollback, and returns the idempotent response.
  4. Cancelled Booking Shield: If a webhook arrives for an already cancelled booking, the event is recorded as IGNORED_CANCELLED and does not mutate booking status.

5. Comprehensive Edge Cases Handled

9. Important Assumptions & Future Enhancements

Design Assumptions

  • Decoupled Pricing: Different centres set independent prices for the same diagnostic test.
  • Immutable Price Snapshot: Booking amounts are captured at booking time and never altered by later price adjustments.
  • 200 OK on Duplicate Webhooks: Standard industry practice (Stripe/Razorpay) to stop provider retries.

What to Improve With More Time

  • Redis Caching: Cache centre catalogs with invalidation triggers.
  • HMAC Webhook Signatures: Cryptographic signatures (X-Signature) with replay protection.
  • Background Job Queues: Celery / ARQ for async notifications and SMS reminders.
  • Slot Locking: Concurrency control for appointment slots.
